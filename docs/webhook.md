# GitHub Webhook & Integration Architecture

This document describes the design, configuration, idempotency model, and verification process for the GitHub Webhook endpoint implemented in Phase 6.

## 1. Overview

The GitHub Webhook integration (`/api/webhook/github`) receives pull request events from GitHub, verifies their authenticity, refreshes PR metadata in FalkorDB, executes change-risk reviews against decisions and incidents, and posts or updates a single markdown review comment on the pull request.

```
 GitHub Delivery
       │
       ▼
[ Signature Check ] ──(Invalid)──▶ 401 Unauthorized
       │ (Valid)
       ▼
[ Event Filtering ] ──(Ping)────▶ 200 { status: "ok", message: "pong" }
       │ (Other/Unsupported)──▶ 200 { status: "ignored" }
       ▼ (pull_request)
[ Payload Schema Validation ] ─(Bad)─▶ 400 Bad Request
       │ (Valid)
       ▼
[ Idempotency Check ] ──(Already Done)──▶ 200 { status: "already_processed" }
       │ (New / Changed Commit)
       ▼
[ Refresh PR Metadata in Graph ] (repo:<owner>/<name>)
       │
       ▼
[ Execute Review Pipeline ] (reviewPullRequest)
       │
       ▼
[ Publish or Update Comment ] (Searches marker <!-- provenance-review -->)
       │
       ▼
[ Update Task State to Done ] (state graph: task:webhook:...)
```

## 3. Webhook Endpoint Specification

- **Path:** `POST /api/webhook/github`
- **Headers:**
  - `x-github-event`: Event type (e.g., `ping`, `pull_request`, `issues`)
  - `x-hub-signature-256`: `sha256=<hex-encoded-hmac>`
  - `x-github-delivery`: Unique delivery UUID generated by GitHub
  - `content-type`: `application/json`

### Supported Events & Actions

- `ping`: Responds with HTTP 200 `{ "status": "ok", "message": "pong" }`.
- `pull_request`:
  - Supported actions: `opened`, `reopened`, `synchronize`, `ready_for_review`.
  - Unsupported actions (`closed`, `labeled`, etc.): Returns HTTP 200 `{ "status": "ignored" }`.
- Other events (`issues`, `push`, etc.): Returns HTTP 200 `{ "status": "ignored" }`.

## 4. Security & Signature Verification

Webhook signatures are verified using strict format validation and constant-time comparison:

1. **Strict Format Enforcement:** The `x-hub-signature-256` header is validated against `/^sha256=[0-9a-f]{64}$/`. Any missing signature, uppercase hex, wrong length (e.g. 63 or 65 hex characters), malformed prefix, or trailing characters are rejected immediately with HTTP 401.
2. **Cryptographic Verification:** Payload raw text is digested with HMAC-SHA256 using `GITHUB_WEBHOOK_SECRET`.
3. **Constant-Time Comparison:** The computed and provided digests are compared as 32-byte binary buffers using `crypto.timingSafeEqual` to prevent timing attacks.
4. **Configuration Safety:** If the secret is missing from server configuration, returns HTTP 500 without leaking details.

## 5. Storage-Guaranteed Atomic Idempotency & Error Recovery

GitHub webhooks may be delivered multiple times due to transient connection retries or concurrent bursts:

1. **Deterministic Task Identifier:**
   `task:webhook:${repository.full_name}:${pr.number}:${pr.head.sha}`
2. **Atomic Storage-Level Claim (`claimWebhookTask`):**
   FalkorDB is an in-memory graph database built on Redis, executing each Cypher command atomically on the single-threaded Redis event loop. Rather than relying on an application-level check-then-act pattern (`getTask()` followed by `createTask()`), the integration issues a single atomic Cypher query:
   ```cypher
   MERGE (t:Task {id: $id})
   ON CREATE SET t.status = 'running', t.created_at = $createdAt, t.type = $taskType,
                 t.repo = $repo, t.scope = $scope, t.remaining_work = $remainingWork,
                 t.completed_steps = '[]', t.claim_action = 'created'
   ON MATCH SET t.claim_action = CASE WHEN t.status = 'failed' THEN 'retried' ELSE 'rejected' END,
                t.error = CASE WHEN t.status = 'failed' THEN null ELSE t.error END,
                t.finished_at = CASE WHEN t.status = 'failed' THEN null ELSE t.finished_at END,
                t.status = CASE WHEN t.status = 'failed' THEN 'running' ELSE t.status END
   RETURN t.id AS id, t.status AS status, t.claim_action AS action
   ```
   - If the task is brand new, it is atomically created with `status: "running"` and `claim_action: "created"`.
   - If the task was previously `failed`, it is atomically reset to `status: "running"` with `claim_action: "retried"`, allowing safe retries.
   - If the task is already `running` or `done`, the claim returns `claim_action: "rejected"`. The webhook handler exits immediately with HTTP 200 `{ "status": "already_processed" }` without executing the review or publishing comments.
   - **Conclusion on Storage Guarantee:** Atomic idempotency **IS guaranteed by the storage implementation** (FalkorDB/Redis command atomicity). Concurrent deliveries cannot interleave between the check and creation.
3. **Reliable Failure Lifecycle Handling:**
   - Metadata refresh (`metadataRefresher`), review execution (`reviewRunner`), and comment publication (`commentPublisher`) are wrapped inside try/catch blocks.
   - Any thrown exception immediately transitions the task in the state graph to `status: "failed"` with a sanitized error message, preventing tasks from remaining permanently stuck in `running`.
   - Sensitive credentials (`GITHUB_TOKEN`, `GITHUB_WEBHOOK_SECRET`, PAT tokens) are scrubbed via `sanitizeSecret` before recording errors.
   - Late failure handlers cannot accidentally overwrite a completed task: `updateTaskState` uses conditional Cypher:
     `SET t.status = CASE WHEN $status = 'failed' AND t.status = 'done' THEN t.status ELSE $status END`.
4. **New Head Commits:**
   When a new commit is pushed, GitHub triggers a `synchronize` event with a new `head.sha`, creating a distinct deterministic task ID while preserving previous history.

## 6. Review Comment Formatting & Safety Guarantees

Comments published to GitHub pull requests adhere to safety rules:

- **Single Comment Policy:** Each comment embeds the marker `<!-- provenance-review -->`. The integration lists existing comments on the PR with bounded retries; if one with the marker is found, it calls `issues.updateComment` instead of creating an additional comment.
- **Incomplete Evidence Warning:** Missing evidence is never reported as safe. If `evidence_status !== "complete"`, a prominent `[!WARNING]` banner is rendered explaining that lack of evidence cannot be treated as safety proof.
- **Signal Breakdown:** Shows blast radius hops, past incident links, active architectural decisions evaluated, and author familiarity.
- **Evidence Paths:** Includes verified graph paths connecting the changed code to dependent callers.

## 7. Local Simulation & Verification

No live GitHub tokens or external repository changes are required for verification. The test suite simulates deliveries using HMAC computation, constant-time verification, and in-memory Octokit clients:

- Test suite: `packages/agents/test/webhook-http.test.ts` (12 tests passed)
  - Signature verification: exact 64-hex lowercase requirement, rejection of non-hex, length 63, length 65, uppercase hex, trailing characters, wrong prefixes, tampered signatures, missing signatures, missing secrets.
  - Ping event pong responses (`200 OK`).
  - Unsupported events (`issues`) and unsupported actions (`closed`).
  - Malformed payload rejection (`400 Bad Request`).
  - Incomplete evidence warnings vs verified status.
  - Comment update idempotency.
- Integration suite: `packages/agents/test/webhook-graph.test.ts` (9 tests passed)
  - Graph PR metadata upsert (`(:Person)-[:AUTHORED]->(:PR)`) in FalkorDB.
  - State graph task lifecycle tracking (`created` -> `running` -> `done`).
  - Synchronize event handling with updated head SHA.
  - Concurrency guards: blocking in-flight duplicate deliveries while task is in `running` state.
  - Simultaneous duplicate deliveries: `Promise.all` launching two identical deliveries concurrently; verifies exactly one review executes and one comment publishes.
  - Retrying failed tasks: retry with identical head SHA successfully claims and processes.
  - Metadata refresh failure: transitions task to `failed` without hanging in `running`.
  - Secret sanitization: scrubs PAT tokens from recorded error strings (`[REDACTED]`).
  - Comment publishing failure: transitions task to `failed`.
  - Status overwrite protection: verifies late failure transition cannot overwrite a `done` task.

## 8. Safe Environment Configuration Guide

Configure these variables in `.env.local`:

| Variable                | Description                                                                   | Safe Default / Recommendation                                                             |
| ----------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `GITHUB_WEBHOOK_SECRET` | Secret key shared between GitHub Webhook and Provenance for HMAC verification | Set a strong random secret (e.g. `whsec_provenance_2026_...`). Never commit to git.       |
| `GITHUB_TOKEN`          | GitHub Personal Access Token (`repo` scope) for reading/updating PR comments  | Required for live PR commenting. Never commit to git.                                     |
| `ENABLE_PR_COMMENTS`    | Gate for posting review comments to GitHub PRs                                | Set `"false"` during development/testing. Set `"true"` only after explicit authorization. |
| `PROVENANCE_GRAPH`      | Target graph prefix in FalkorDB                                               | Defaults to `repo:<owner>/<name>`. Can be overridden for testing (e.g. `test:<repo>`).    |

## 9. Live Webhook Integration Test Guide & Status

### Current Status: **BLOCKED / NOT TESTED** (Awaiting Live Public HTTPS Tunnel & Test Repository Authorization)

Local handler, cryptographic verification, FalkorDB ingestion, idempotency, and comment updates are **100% Verified** locally. Live public delivery requires the following manual steps on a dedicated non-production test repository:

1. **Start the local Web Server**:

   ```powershell
   node apps/web/node_modules/next/dist/bin/next dev --webpack --hostname 127.0.0.1 --port 3100
   ```

2. **Expose a Temporary Public HTTPS Tunnel**:
   Using `cloudflared` (recommended, no account required) or `ngrok`:

   ```powershell
   cloudflared tunnel --url http://127.0.0.1:3100
   # Or: ngrok http 3100
   ```

3. **Configure Webhook on a Test GitHub Repository**:
   - Navigate to **Your Test Repo** $\rightarrow$ **Settings** $\rightarrow$ **Webhooks** $\rightarrow$ **Add webhook**.
   - **Payload URL**: `https://<tunnel-domain>/api/webhook/github`
   - **Content type**: `application/json`
   - **Secret**: The value from `GITHUB_WEBHOOK_SECRET` in `.env.local`.
   - **Which events**: Select **Let me select individual events** $\rightarrow$ check **Pull requests**.

4. **Verify GitHub Ping Delivery**:
   - Upon saving, GitHub immediately sends a `ping` event.
   - Check the **Recent Deliveries** tab in GitHub: verify the response code is `200 OK` with body `{"status":"ok","message":"pong"}`.

5. **Test PR Lifecycle**:
   - Open a test Pull Request on your test repository.
   - Verify the delivery succeeds (`200 OK`) and PR metadata is ingested into FalkorDB.
   - If `ENABLE_PR_COMMENTS="true"`, verify that a single review comment is posted with marker `<!-- provenance-review -->`.
   - Push a new commit to verify `synchronize` updates the comment rather than creating a duplicate.
